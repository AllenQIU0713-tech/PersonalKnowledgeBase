## 交接循环

1. 开发按可独立运行和验证的功能切分批次。每批达到可测条件，保存交付说明，并在开发任务明确声明“批次 X 开发完成，可以开始该批次测试”，主动通知测试任务。
2. 交付说明记录批次编号、确定的 Git 提交或稳定代码快照、实现范围、对应需求、启动命令、配置与数据前提、已知限制及尚未实现范围。没有执行的验证必须标为未验证，不能声称通过。
3. 测试针对该版本执行验证，在 docs/ 下保存报告并将结果通知开发任务；不得将后续开发中的代码混入已交付版本的测试结果。
4. 开发读取报告，修复问题并记录对应问题编号，交付新的版本供复测。无依赖冲突的下一批开发可与上一批测试并行。
5. 如测试与开发共用目录，使用独立检出目录及测试数据目录，或协商稳定窗口；不得在测试运行中切换其工作目录版本或修改其测试数据。
6. 根据用户于 2026-09-24 的补充要求，每批测试完成后，测试主动通知审计任务“批次 X、版本 Y 测试完成，可以开始该批次安全合规审计”，附交付说明、测试报告路径、测试结论、未解决问题及未验证项，不等待全部开发或所有批次测试结束。测试完成不等于测试通过；存在失败或阻塞项时如实交接，不将其表述为可发布。
7. 审计针对同一版本保存报告并反馈开发和测试。需整改的问题由开发修复，测试对新版本复测后再交审计复审；各角色按批次、版本和报告去重，普通规则同步或确认消息不触发测试或审计。
8. 根据用户于 2026-09-24 在审计任务中的明确要求，审计发现问题后，必须主动通知「实施产品设计方案」任务，对产生问题的点重新设计并实现整改，同时抄送测试任务。交接包含问题编号、批次和版本、证据、风险等级、受影响范围及复审验收条件。开发交付时说明根因、重新设计的处理方式及对应问题编号，提供新版本；随后进入“开发重新设计与整改 → 测试复测 → 审计复审”的新循环。审计逐项核实关闭情况，未满足验收条件的问题保持未关闭，阻断放行的问题未关闭前不作通过结论。

测试尚未收到批次交付时无需启动测试。每次批次交付与修复复测均应去重，避免自动监控与主动通知触发重复工作。
